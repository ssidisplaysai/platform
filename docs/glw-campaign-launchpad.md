# GLW Campaign Launchpad

Campaign Launchpad is the reach-first GLW workflow for evaluating a product campaign before execution. The operator selects desired reach, submits a canonical product URL as an onboarding seed, and reviews Genesis authority, coverage, conflicts, publication policy, and safe target capacity.

V1 is read-only. `POST /api/glw/campaign-launchpad/preflight` authenticates the workspace request, accepts only HTTP(S) URLs, resolves the URL against the registered site and product repositories, and reuses the existing GLW canonical target preflight. It can issue registered WordPress API reads but has no campaign, product, source-authority, publication, or WordPress mutation path. The Launch Campaign control remains disabled.

Maximum Safe Reach is the number of targets that every required current authority affirmatively certifies. Targets with incomplete authority are blocked rather than inferred safe.

V2 keeps execution and campaign ownership separate. The GLW page-execution journal provides checked execution ownership and exposes only job/execution IDs. This upstream has no authoritative campaign persistence, so campaign ownership is `UNAVAILABLE` and never inferred from execution records. Site and product readiness delegate to the canonical Genesis readiness evaluators without redefining their rules.

Current reach modes plan city targets from the existing GLW registry. For a city target, cannibalization `CLEAR` requires authoritative exact-canonical absence, a `CREATE_CITY` decision from the existing matrix planner (including its unique parent-state rule), and authoritative broader product/geographic intent clearance. State reach and metro/local reach select supported city targets; standalone state targets and other target classes are not generated by Launchpad V2. This upstream has no broader intent authority, so production cannibalization authority is `UNAVAILABLE` and safe reach remains zero. Public WordPress zero-result reads also do not certify absence because non-public drafts may exist.

Each potential target receives exactly one primary disposition: existing coverage, execution-owned, campaign-owned, cannibalization conflict, authority-blocked, unreconciled, unsupported, or safe. Headline counts and the exclusion drilldown derive from those records, so their sum equals potential reach. Exact-canonical conflict counts remain overlapping diagnostics and are labeled separately.

V3 re-runs preflight immediately before launch, then sends the exact selected city identities to the certified atomic campaign endpoint. Preflight remains operator planning authority; the runtime reservation is final mutation-time ownership authority and closes the concurrency boundary. Launchpad never supplies a launch ID, campaign ID, safety flag, alternate city, direct-publish instruction, activation request, or dispatch request.

V2.5 converges the existing Genesis campaign persistence format through a read-only adapter. Configure `GLW_CAMPAIGN_AUTHORITY_PERSISTENCE_DIR` with the directory containing `glw-campaign-repository.json` and `glw-campaign-target-repository.json`; `GCP_FOUNDATION_PERSISTENCE_DIR` is accepted when Launchpad shares the runtime persistence root. The adapter reads versioned envelopes without seeding or writing them. Missing or malformed authority remains unavailable.

Campaign ownership uses exact organization, site, product, page type, state, and city identity. All persisted runtime target states retain ownership. A failed target is unreconciled and reserved until the existing recovery/reconciliation workflow changes it; failure never implies availability. Broader city intent authority uses the same checked target index and the existing GLW city registry to detect exact intent owners, duplicate claims, and alternate-slug ownership of the same product and city. It does not use keyword or similarity heuristics.

The persisted format is the existing Genesis campaign authority introduced by `03ae6b90` and its target queue from `e0a4e5f8`, including city target identity support from `29cb4e2a`. Launchpad does not copy campaign mutation services. It reads the same schema-versioned campaign and target envelopes through `campaign-authority.ts`. Deterministic broader intent clearance requires a unique GLW city registry identity and no exact or alternate-slug owner in that checked target index, in addition to canonical preflight and matrix hierarchy checks.

## V3 atomic launch integration

Analyze remains read-only and operator-visible. The configured adapter first repeats `POST /api/glw/campaign-launchpad/preflight`, requires the same ready site, product, runtime policy, and exact selected safe city cohort, and then calls the single certified `POST /api/glw/campaign-launch` endpoint. The launch request contains the explicit `LAUNCH_CITY_CAMPAIGN` operation, site, product, human campaign name, bounded pages-per-day value, exact city targets, and publication-policy acknowledgement. Runtime campaign policy authority, global ownership, all-or-nothing reservation, launch ID, campaign ID, idempotency, and recovery remain server-owned.

The UI covers confirmation, immediate revalidation, atomic reservation, and reference bootstrap progress. Durable outcomes distinguish campaign creation at `REFERENCE_PENDING`, existing idempotent campaigns, reference review, active/dispatch states, and recovery required. A reference-review result means the campaign exists and awaits the existing manual review flow, not that launch failed. Recovery results preserve the campaign ID and warn that another campaign must not be created. Atomic target conflicts state that no new cohort was partially reserved and offer Analyze Again. Metrics unavailable from the current read model are shown as unavailable rather than inferred.

Production launch remains disabled. Both capability resolvers reject execution under `NODE_ENV=production`. Isolated development can enable the real adapter with `GLW_LAUNCHPAD_ATOMIC_LAUNCH=true`, or the non-mutating visual fixture with `GLW_LAUNCHPAD_SYNTHETIC_LAUNCH=true`. The synthetic adapter exists only to certify UX behavior and never calls a launch endpoint. The atomic endpoint creates a draft campaign and durable reference-pending journal state; it does not publish, dispatch, or bypass existing manual reference approval.
