# GLW Campaign Launchpad

Campaign Launchpad is the reach-first GLW workflow for evaluating a product campaign before execution. The operator selects desired reach, submits a canonical product URL as an onboarding seed, and reviews Genesis authority, coverage, conflicts, publication policy, and safe target capacity.

V1 is read-only. `POST /api/glw/campaign-launchpad/preflight` authenticates the workspace request, accepts only HTTP(S) URLs, resolves the URL against the registered site and product repositories, and reuses the existing GLW canonical target preflight. It can issue registered WordPress API reads but has no campaign, product, source-authority, publication, or WordPress mutation path. The Launch Campaign control remains disabled.

Maximum Safe Reach is the number of targets that every required current authority affirmatively certifies. Targets with incomplete authority are blocked rather than inferred safe.

V2 keeps execution and campaign ownership separate. The GLW page-execution journal provides checked execution ownership and exposes only job/execution IDs. This upstream has no authoritative campaign persistence, so campaign ownership is `UNAVAILABLE` and never inferred from execution records. Site and product readiness delegate to the canonical Genesis readiness evaluators without redefining their rules.

Current reach modes plan city targets from the existing GLW registry. For a city target, cannibalization `CLEAR` requires authoritative exact-canonical absence, a `CREATE_CITY` decision from the existing matrix planner (including its unique parent-state rule), and authoritative broader product/geographic intent clearance. State reach and metro/local reach select supported city targets; standalone state targets and other target classes are not generated by Launchpad V2. This upstream has no broader intent authority, so production cannibalization authority is `UNAVAILABLE` and safe reach remains zero. Public WordPress zero-result reads also do not certify absence because non-public drafts may exist.

Each potential target receives exactly one primary disposition: existing coverage, execution-owned, campaign-owned, cannibalization conflict, authority-blocked, unreconciled, unsupported, or safe. Headline counts and the exclusion drilldown derive from those records, so their sum equals potential reach. Exact-canonical conflict counts remain overlapping diagnostics and are labeled separately.

V3 must re-run preflight immediately before enqueue, then pass `siteId`, `productId`, `reach`, exact selected target identities (`canonicalPath`, `stateCode`, `citySlug`), authoritative publication policy, and selected bounded batch size into the existing page-generation execution service. The repository has no certified authority revision or compare-and-swap fingerprint, so V3 must not invent one; it must rely on immediate revalidation and existing execution identity/collision guards. It must not introduce separate campaign persistence or targeting logic.
